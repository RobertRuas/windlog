The repository is split into two co-located layers under a single root:

- Backend (`API/`): NestJS application bootstrapped from `src/main.ts`, which registers global middleware (Helmet, compression, CORS), a global `ValidationPipe`, `HttpExceptionFilter`, `TransformInterceptor`, and `LoggingInterceptor`. The root `AppModule` imports all feature modules (`AuthModule`, `UsersModule`, `ProjectsModule`, `UploadModule`, `NotificationsModule`, `WeeklyTimesheetModule`, `FeedbackModule`, `SystemLogModule`). Each feature module follows the strict `{name}.module.ts` + `{name}.controller.ts` + `{name}.service.ts` layout with DTOs under `dto/`. Prisma client is provided via a shared `database/prisma.service.ts` and types are generated to `prisma/generated/prisma`.
- Frontend (`src/`): React app bootstrapped from `main.tsx`, wrapped in `QueryClientProvider` and `BrowserRouter`. `App.tsx` defines all routes guarded by `ProtectedRoute`, `AuthOnlyRoute`, `AdminRoute`, and `AdminOrHRRoute` wrappers that read JWT from localStorage. Pages live under `pages/<feature>/` with colocated `components/` and `hooks/`; cross-cutting UI lives in `components/ui/` and `components/layout/`. Data access is centralized in `services/*.ts` (one per domain) which call the NestJS API; TanStack Query keys follow the `['entity', filter?]` / `['entity', id]` convention.

Dependency direction is strictly one-way: frontend services → NestJS controllers → services → PrismaService → PostgreSQL. Cross-cutting concerns (validation, logging, response transformation, auth guards/strategies) are implemented as NestJS decorators/interceptors/filters rather than scattered logic.
