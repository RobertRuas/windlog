The repository is split into two top-level layers:

- Backend (`API/src`): A NestJS application organized around feature modules under `modules/<name>/`, each following the strict `{name}.module.ts` + `{name}.controller.ts` + `{name}.service.ts` + `dto/{name}.dto.ts` layout. The root `AppModule` wires all modules (Auth, Users, Projects, Upload, Notifications, WeeklyTimesheet, Feedback, SystemLog). Cross-cutting concerns live in `common/` (guards, decorators, DTOs, filters, interceptors, pipes) and are registered globally from `main.ts`, which also configures Helmet, compression, CORS, global ValidationPipe, Swagger, and the LoggingInterceptor that maps HTTP requests to `LogAction` entries via `determineAction()`.
- Database: Prisma v7 with `@prisma/adapter-pg` against PostgreSQL; `PrismaService` extends `PrismaClient` and is injected into services. All business entities use soft delete via `deletedAt` fields, and enums in code mirror `schema.prisma` enums.
- Frontend (`src/`): React app bootstrapped in `main.tsx` with `App.tsx` defining routes wrapped by role-based guards (`ProtectedRoute`, `AdminRoute`, `AdminOrHRRoute`). Pages follow `{PageName}.tsx` + `components/` + `hooks/` structure. Data access goes through typed service files in `src/services/*.ts` which call a centralized `api.ts` fetch wrapper that injects JWT Bearer tokens and auto-logs out on 401. TanStack Query keys follow `['entity', filter?]` / `['entity', id]` convention and mutations invalidate related keys.

Dependency direction is strictly one-way: frontend services → backend controllers → services → PrismaService → PostgreSQL. Modules only import shared `common/` utilities and their own DTOs.
